## 1. Resumen Ejecutivo

El proyecto construye un panel de datos satelitales multi-fuente sobre Cali + corredor industrial Yumbo-Acopi (bbox `[-76.65, 3.30, -76.30, 3.65]`, ventana 2021-2026) con destino a modelado ML (CLIP + SAE para interpolacion espacial de calidad del aire). El panel combina 6 fuentes de Google Earth Engine, almacenadas en formato dual GeoTIFF + Zarr tanto en Google Cloud Storage como en HuggingFace Hub.

**Volumen actual**: ~77 GB comprimido (umbral del proyecto: >= 50 GB). Cumplido.

**Estado general**: La fase de adquisicion de datos esta funcional y en produccion. El pipeline exporta datos a GCS y HF con paralelismo, cache de reanudacion y logs estructurados. La documentacion tecnica en `docs/` es de buena calidad. Quedan pendientes la integracion de datos DAGMA/SISAIRE (ground truth) y las fases de modelado (Situacion 2: CLIP+SAE, Situacion 3: Kriging).

## 3. Arquitectura del Pipeline

```
google-earth/config.py (constantes centrales)
        |
        ├── gcp/exportar_*.py
        │       └── GEE getDownloadURL() -> GCS (GeoTIFF + Zarr)
        │
        ├── hugging-face/subida_masiva.py
        │       └── GEE -> local -> apilar -> Zarr -> HuggingFace
        │
        └── google-earth/imagenes-cali/
                └── Exploracion, pesos, thumbnails
```

**Flujo de datos**:
1. Scripts consultan `ee.ImageCollection` por fuente
2. Descarga banda-por-banda via `getDownloadURL()` con streaming directo a GCS o staging local
3. Las bandas individuales se apilan en GeoTIFF multi-banda
4. Se construye Zarr con Dask (chunking lazy)
5. Se sube a HuggingFace via `HfApi.upload_large_folder()`

## 5. Evaluacion de Calidad

### 5.1 Fortalezas

1. **Documentacion excepcional**: `docs/DATASETS.md` (287 lineas, 6 fuentes detalladas con justificaciones), `docs/PESOS_PIPELINE.md` (224 lineas, analisis de compresion con benchmarks reales), `docs/BANDAS_JUSTIFICACION.md`, `docs/JUSTIFICACION_FORMATO.md`. Cada decision tecnica tiene su razonamiento explicito y referencias a fuentes externas.

2. **Pipeline robusto**: Manejo de errores con try/except por operacion individual (no aborta el lote), cache de ids ya procesados (reanudacion), verificacion de disco libre, respeto de rate limits.

3. **Modulo de logging propio**: `logger/__init__.py` (28 lineas) provee logging dual (archivo + consola) con timestamps. Todos los scripts lo usan consistentemente.

4. **Configuracion centralizada**: `google-earth/config.py` es la unica fuente de verdad para bbox, fuentes, bandas, escalas y disponibilidad. Todos los scripts importan de ahi.

5. **Paralelismo**: `ThreadPoolExecutor` con 4-16 workers en todas las operaciones de descarga.

6. **Formato dual justificado**: GeoTIFF como source-of-truth, Zarr como vista analitica. No es duplicacion ingenua — es cambio de estructura de acceso (chunking multidimensional). Documentado en `docs/JUSTIFICACION_FORMATO.md`.

### 5.2 Problemas

#### Criticos

1. **`google-earth/_init_.py` no es `__init__.py`**: El archivo se llama `_init_.py` (underscores rodeando init), lo que significa que `google-earth/` NO es un paquete Python importable. Esto obliga al patron de `sys.path.insert` en todos los scripts. Si fue intencional (para evitar que sea paquete), deberia documentarse. Si fue un error de nombrado, deberia corregirse.

2. **Sin tests automatizados**: Solo existe `gcp/test_s2_tocloudstorage.py` como script de validacion manual. No hay tests unitarios, de integracion, ni de regresion. Cualquier cambio futuro en el pipeline carece de red de seguridad.

3. **README.md vacio**: El archivo README.md tiene 0 lineas. El proyecto tiene excelente documentacion interna pero ninguna puerta de entrada para nuevos colaboradores.

#### Importantes

4. **Hacks de `sys.path` proliferados**: Cada script repite el mismo boilerplate de manipulacion de `sys.path` con numeros inconsistentes de `os.path.dirname()`. Esto es fragil: si la estructura de directorios cambia, hay que tocar cada script.

   ```python
   # Variante A (gcp/exportar_a_gcs.py):
   ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))

   # Variante B (google-earth/imagenes-cali/calcular_peso_cali.py):
   HERE = os.path.dirname(os.path.abspath(__file__))
   sys.path.insert(0, os.path.dirname(HERE))
   sys.path.insert(0, os.path.dirname(os.path.dirname(HERE)))
   ```

5. **Codigo duplicado entre exportadores**:
   - `exportar_s2.py` y `exportar_s2_final.py` tienen logica casi identica (difieren en agrupacion de bandas)
   - `calcular_peso_cali.py` y `calcular_peso_cali_completo.py` solapan funcionalidad
   - El calculo de BYTES_DTYPE y pixeles_recorte aparece duplicado en 3+ archivos sin modulo compartido

6. **Valores hardcodeados**: `PROJECT_ID`, `BUCKET_NAME`, `MAX_WORKERS`, `BATCH_SIZE` estan en el codigo fuente en lugar de variables de entorno o configuracion externalizada.

#### Menores

7. **`# type: ignore[reportMissingImports]` en cada import**: El efecto practico es que no hay type checking funcionando en el proyecto. Esto es consecuencia del problema #4 (sys.path hacks).

8. **Archivo `docs/DISPONIBLIDAD_DATOS.txt`**: Contiene notas informales con lenguaje no profesional.

9. **Sin CI/CD**: No hay GitHub Actions, GitLab CI, ni automatizacion de despliegue. Las ejecuciones dependen de sesiones manuales (`screen`/`tmux`) en un servidor remoto.

10. **Sin Docker/containerizacion**: La dependencia de `earthengine-api` y `gcloud` hace que la configuracion del entorno sea manual y propensa a drift entre maquinas.

11. **Dos pipelines paralelos a GCS y HF**: No esta claro si es redundancia intencional o dos experimentos paralelos. Si ambos se mantienen, deberia documentarse la estrategia (GCS = almacenamiento primario, HF = distribucion/publicacion?).

### 5.3 Seguridad

| Issue | Severidad | Estado |
|-------|-----------|--------|
| `.env` contiene token HF vivo (`hf_qfa...`) | Alta | En disco, gitignored |
| `.claude/settings.local.json` expone IP de servidor | Media | En disco |
| Token comentado de otro usuario en `.env` | Baja | Fuga potencial |

El `.env` esta en `.gitignore`, por lo que no se versiona. Sin embargo, permanece en el sistema de archivos local y cualquier copia del repositorio que incluya el `.env` filtraria el token.

## 8. Recomendaciones

### Inmediatas (antes de seguir desarrollando)

1. **Rotar el token de HuggingFace**. El token `hf_qfa...` visible en `.env` debe invalidarse y regenerarse.
2. **Escribir README.md**. Minimo: titulo, proposito, arquitectura, como ejecutar, dependencias.
3. **Renombrar `_init_.py` a `__init__.py`** o documentar por que no es un paquete. Si se convierte en paquete, eliminar los `sys.path.insert` de todos los scripts.

### Corto plazo

4. **Unificar los exportadores de S2** (`exportar_s2.py`, `exportar_s2_final.py`) en un solo script con parametros.
5. **Crear un modulo `utils.py`** con `BYTES_DTYPE`, `pixeles_recorte()`, `ancho_alto_metros()` para eliminar duplicacion.
6. **Agregar tests de humo**: al menos verificar que `config.py` importa limpiamente, que las 6 fuentes son accesibles, que las bandas declaradas existen en GEE.

### Mediano plazo

7. **Integrar DAGMA/SISAIRE**: scraping o descarga manual de las 9 estaciones, formato comun con el panel satelital.
8. **Implementar una capa de acceso a datos**: modulo `datasets.py` que exponga `open_dataset(fuente)` devolviendo `xr.Dataset` desde GCS o HF.
9. **Containerizar**: Dockerfile con `earthengine-api`, `gcloud`, y dependencias del proyecto.

### Largo plazo

10. **CI/CD**: GitHub Actions que ejecute tests, type checking, y validacion de que las fuentes GEE siguen accesibles.
11. **Migrar de `getDownloadURL` a `xee`** si el rendimiento se vuelve cuello de botella (xee permite lazy loading directo a xarray sin descarga intermedia).
